# VulnArena 系统设计（总计划）

> 本文件取代 `ADR-001`、`ADR-002`、`ADR-003`。三份 ADR 的结论已并入本文；
> 之后的架构调整直接改这里，不再单开文件。

- 版本：v2（2026-10-28，从"多业务域薄靶场"转为"单业务域深系统"）
- 目标读者：项目作者本人

---

## 1. 一句话定义

**一个可自建、可复现、可跟练的企业级安全演练台**：里面跑着一套像真的采购审批系统，
红队打它、蓝队修它，学习者能看懂每一步为什么成立，也能自己动手重打一遍。

不是"漏洞集合"，是"一个系统 + 一条入侵路径"。

## 2. 非目标（明确不做）

- 不做通用的漏洞扫描器 / 攻击平台，不接任意外部目标
- 不追求语言数量，先把一种语言做透，再按 manifest 扩展
- 不做多租户 SaaS、不做 K8s、不做生产级高可用
- 不为了"看起来高级"引入 Kafka / ES / 微服务

## 3. 总体架构

```
┌───────────────────────────────┐          ┌────────────────────────────────┐
│ 主核 Core（真实数据）          │          │ 靶场 Arena（可丢弃）            │
│ NVD 情报 · 检索 · 知识卡        │  事件总线 │ 采购审批系统（被攻击对象）      │
│ 观战台 · 演练历史               │◄────────►│ 自适应网关 · 红蓝编排 · 跟练     │
└───────────────────────────────┘  Redis    └────────────────────────────────┘
           ▲                                            │
           └────────── 控制指令（start/restore）─────────┘
```

三条硬边界（沿用 ADR-001）：

1. 靶场只发布事件，不读主核的 `vulnerabilities` 表；
2. 主核只发指令、只订阅事件，不 import 靶场内部；
3. 删掉靶场全部数据，主核毫发无损。

## 4. 业务域：采购审批（唯一域，做深）

### 4.1 角色

| 角色 | 权限 |
|---|---|
| `employee`（alice / bob） | 发起采购单、看自己的单、传附件 |
| `manager`（mike） | 审批 5 万以下 |
| `finance`（fiona） | 复核 5~50 万，执行付款 |
| `cfo`（admin） | 审批 50 万以上 |
| `auditor`（audit） | 只读审计日志 |

### 4.2 状态机

```
DRAFT ──submit──► MANAGER_REVIEW ──approve──► FINANCE_REVIEW ──approve──► CFO_REVIEW ──approve──► APPROVED ──pay──► PAID
                      │                          │                          │
                      └──── reject ──► REJECTED ◄┘                          └──► REJECTED
```

金额决定跳级：≤5 万只需 manager；5~50 万需 manager+finance；>50 万需三人。
**状态与金额的一致性由服务端校验**——这正是可被攻击的逻辑面。

### 4.3 数据模型（内存 SQLite）

| 表 | 关键字段 |
|---|---|
| `users` | id, name, role, department, phone, tenant |
| `purchase_orders` | id, tenant, requester, title, amount, supplier_id, status, attachment, created_at |
| `approvals` | id, po_id, actor, role, decision, comment, created_at |
| `suppliers` | id, name, bank_account, callback_url, level |
| `secrets` | id, name, value（内含 canary） |
| `audit` | id, ts, actor, role, method, path, status, jti |

**数据因果（A+B 的核心）**：上一阶段的产出是下一阶段的输入。

```
员工手机号（越权可见） → 重置口令的输入
供应商 callback_url（越权可见） → SSRF 的目标
附件 id（列表可见） → 路径穿越的入口
审批单号（列表可见） → 状态机绕过的入口
```

### 4.4 任务目标（可判定）

每场演练生成一个 mission，**判定查数据库状态，不查响应文本**：

```
mission: "以 CFO 身份，让一笔 ≥80 万的采购单只经过一个人就变成 PAID"
verify:  exists PO where amount >= 800000 and status == PAID
         and count(approvals where po_id = PO) == 1
```

达成才算赢；只拿到 canary 不算。

## 5. 漏洞模型（6 类，全部长在业务流程上）

| 缺陷开关 | 业务表现 | 类别 | 网关能否拦 |
|---|---|---|---|
| `sqli_search` | 采购单搜索拼接 SQL | SQLi | ✅ 能 |
| `sqli_login_bypass` | 登录注释密码校验 | SQLi | ✅ 能 |
| `idor_po_detail` | 直接按 id 读别人的单 | 越权 | ❌ 只能改代码 |
| `mass_assignment` | 审批接口接受 `approver` 字段 | 越权/逻辑 | ❌ 只能改代码 |
| `state_skip` | 审批接口不校验状态机 | 逻辑 | ❌ 只能改代码 |
| `path_traversal` | 发票附件路径未归一化 | 路径穿越 | ❌ 只能改代码 |
| `ssrf_supplier` | 供应商回调地址未限制 | SSRF | ✅ 能 |

> 网关能拦的只有 3 个，另外 4 个必须改代码——这个比例本身就是要教给学习者的。

## 6. 演练流程（四阶段）

1. **布防**：蓝队开启缺陷组合（默认全开，保证每类至少一个），预置一条"年久失修"的弱规则；
2. **攻击**：红队按 kill chain 逐步推进（探测 → 绕过 → 越权 → 触达目标）；
3. **修复**：蓝队对能上网关的出规则（过闸门：召回 100%、误杀 0%），其余切代码；
4. **回归**：重放攻击（全 4xx）+ 正常业务（全 200），双断言通过才算 `VERIFIED`。

每一步都发事件，观战台与跟练共用同一条时间线。

## 7. 教学模型（三级提示）

跟练不再是"给答案"，而是分级：

| 级别 | 给什么 |
|---|---|
| L1 任务 | 目标 + 已知情报（角色、端点清单、正常请求示例） |
| L2 思路 | 卡住 5 分钟后："注意这个参数被直接拼进 SQL" |
| L3 命令 | 再卡住才给可复制的请求 |

进度、提示消耗都记在会话里，用于复盘"你是怎么攻破的"。

## 8. 多语言扩展（暂缓，保留接口）

每个语言 = 一个独立靶场模块，共享契约（缺陷头、canary、错误形状），业务场景各自不同：

| 靶标 | 语言 | 场景 | 状态 |
|---|---|---|---|
| python-procure | Python | 采购审批（当前唯一实现） | ✅ |
| go-gateway | Go | 云原生边缘网关 | 待做 |
| php-cms | PHP | 传统建站 | 待做 |
| java-ledger | Java | 交易与账务 | 待做 |

`TargetManifest` 是唯一事实来源；新增语言 = 一条 manifest + 一个小服务。

## 9. 存储与安全边界

- 靶场数据：进程内 SQLite + 虚拟文件系统，可整体丢弃；
- 演练历史：PostgreSQL `arena_reports`（JSONB），主核可查；
- 事件：Redis List（不可用时自动降级为内存）；
- 红线：禁止 `eval/exec/os.system/subprocess`、禁止真实出网、禁止读真实文件、控制面仅本机。

## 11. 验收标准

- `ruff` / `pytest` 全绿，覆盖率 ≥ 80%（带 `TEST_DATABASE_URL`）
- 一条命令跑完闭环：布防 → 攻击 → 修复 → 回归 → mission 判定
- 关掉任一条规则，回归必须变红（证明断言有效）
- 至少 4 个缺陷是"网关拦不住、只能改代码"的
- 新手能在 30 分钟内跟完一场而不需要外部资料
